1Branching, merging, rebasing, conflict resolution

Branching
git branch                          # list local branches
git checkout -b feature/backup-script    # create and switch
git switch -c feature/backup-script      # same thing, newer syntax
git branch -d feature/backup-script      # delete a merged branch
git branch -D feature/backup-script      # force-delete an unmerged branch
Merging
git checkout main
git merge feature/backup-script      # fast-forward if possible, otherwise a merge commit
git merge --no-ff feature/backup-script    # always create a merge commit, even if fast-forward is possible
git log --oneline --graph --all      # visualize branch history
Rebasing
git checkout feature/backup-script
git rebase main                      # replay your commits on top of main's latest
git rebase -i HEAD~3                 # interactive rebase — squash/reword/reorder last 3 commits

# If a rebase goes wrong and you want out:
git rebase --abort
Resolving a conflict
# git merge or rebase stops and marks the file:
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature/backup-script

# Edit the file to the version you want, removing the markers, then:
git add config.yml
git merge --continue      # if you were merging
git rebase --continue      # if you were rebasing
Merge vs rebase — when to use which

Rebase your own feature branch to keep history linear before opening a PR. Never rebase a branch that others have already pulled from — it rewrites commit hashes and breaks their history. Merge (not rebase) when integrating a shared branch like main.

2Open a PR against a public repo; practice code review etiquette

Fork, branch, push, open a PR
gh repo fork some-org/some-project --clone
cd some-project
git checkout -b fix/typo-in-readme

# make your change
git add README.md
git commit -m "Fix typo in installation section"
git push -u origin fix/typo-in-readme

gh pr create --title "Fix typo in installation section" \
  --body "Small doc fix — 'recieve' to 'receive' in the install steps."
Reviewing someone else's PR
gh pr list --repo some-org/some-project
gh pr checkout 42 --repo some-org/some-project   # pull their branch locally to test it
gh pr diff 42
gh pr review 42 --approve --body "LGTM, tested locally."
gh pr review 42 --request-changes --body "See inline comment on error handling."
Code review etiquette

Start with something specific you liked, not just critique. Ask questions ("what happens if this input is empty?") rather than issuing commands ("add a null check"). Keep feedback about the code, not the author. Small, focused PRs get reviewed faster and merged faster than large ones — this applies to your own PRs too.

3Set up a GitHub org for the capstone project — start it now

The capstone in Phase 8 pulls together everything from every phase. Starting the org and repo now means eleven months of commits by the time you need it as a portfolio piece — that history is itself evidence of consistency.

Create the org and seed repo
# Via the GitHub UI: github.com/account/organizations/new (free tier is enough)

# Then, locally:
gh repo create your-org/capstone-project --public \
  --description "54-week DevOps roadmap capstone: cloud-native app on AWS" \
  --clone

cd capstone-project
mkdir -p docs infra/terraform src .github/workflows
echo "# Capstone Project" > README.md
git add -A
git commit -m "Initial capstone repo structure"
git push -u origin main
Checkpoint

The org and repo exist, have a README describing the eventual project (even as a rough draft — you'll refine it every phase), and branch protection is on for main (Settings → Branches → require PRs before merge). Treat it like a real team repo from day one.

4Move your break/fix log into the repo and commit to it weekly

You started this log in Week 1. Move it into version control now so it becomes a searchable, dated record instead of scattered notes.

Set it up
cd capstone-project
mkdir -p docs
mv ~/notes/break-fix-log.md docs/break-fix-log.md
git add docs/break-fix-log.md
git commit -m "Add break/fix log tracking the roadmap"
git push
A weekly habit worth automating later (Phase 6 territory, but start the habit now)
# Every Friday:
cd capstone-project
$EDITOR docs/break-fix-log.md      # add this week's entries
git add docs/break-fix-log.md
git commit -m "Break/fix log: Week $(date +%V)"
git push
Checkpoint

Run git log --oneline -- docs/break-fix-log.md at the end of Phase 0 and see at least six weekly commits. This log becomes one of the most concrete things you can point to in an interview — "here's every mistake I made and how I fixed it, dated and public."
