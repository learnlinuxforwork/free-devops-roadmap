1Build a workflow: lint → test → build image → push to ECR → deploy to EKS

A complete GitHub Actions workflow tying the whole roadmap together
name: ci-cd
on:
  push: { branches: [main] }
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ruff pytest
      - run: ruff check .
      - run: pytest
  build-and-push:
    needs: ci
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: ${{ secrets.DEPLOY_ROLE_ARN }}, aws-region: us-east-1 }
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr
      - run: |
          docker build -t ${{ steps.ecr.outputs.registry }}/roadmap-api:${{ github.sha }} .
          docker push ${{ steps.ecr.outputs.registry }}/roadmap-api:${{ github.sha }}
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - run: |
          helm upgrade roadmap-api ./charts/roadmap-api \
            --set image.tag=${{ github.sha }} -n roadmap

Notice the deploy step doesn't run kubectl apply directly against the cluster — it updates the Helm values and, if you're running ArgoCD from Week 32, pushing that change to Git is enough; ArgoCD picks it up. Either approach is fine, but be consistent.

Checkpoint

Push a commit with a deliberately failing test and confirm the pipeline stops at the ci job — no image ever gets built or pushed for code that doesn't pass.

2Optional: stand up Jenkins in a container to compare self-hosted vs managed CI

Jenkins in a container, fastest path to a running instance
docker run -d --name jenkins -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
A minimal declarative Jenkinsfile, same shape as the GitHub Actions workflow above
pipeline {
  agent any
  stages {
    stage('Test') { steps { sh 'pytest' } }
    stage('Build') { steps { sh 'docker build -t roadmap-api:$GIT_COMMIT .' } }
    stage('Push')  { steps { sh 'docker push roadmap-api:$GIT_COMMIT' } }
  }
}
The tradeoff, in one table
GitHub Actions   Zero infra to manage, generous free tier, tied to GitHub
Jenkins          You own patching/scaling/plugins, but full control and any Git host
Checkpoint

You don't need to keep Jenkins running — the point was feeling the operational difference firsthand. Tear it down: docker rm -f jenkins.
