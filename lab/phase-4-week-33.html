1Horizontal Pod Autoscaler, Cluster Autoscaler/Karpenter

HPA — scale Pod count on a metric
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: roadmap-api, namespace: roadmap }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: roadmap-api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
Cluster Autoscaler / Karpenter — scale the nodes underneath the Pods
# Karpenter NodePool (modern replacement for Cluster Autoscaler on EKS)
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: default }
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
  limits: { cpu: 100 }

HPA answers 'do I have enough Pods for the load,' Cluster Autoscaler/Karpenter answers 'do I have enough nodes to schedule those Pods.' You need both layers — HPA alone just leaves Pods stuck Pending if the cluster has no room to place them.

2Pod disruption budgets, resource requests/limits, readiness/liveness probes

Resource requests and limits — the scheduler and kubelet both depend on these
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits:   { cpu: "500m", memory: "256Mi" }
Probes — Kubernetes needs to know the difference between 'starting up' and 'broken'
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }
          initialDelaySeconds: 5
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 15
          periodSeconds: 10
PodDisruptionBudget — protect availability during voluntary disruptions (node drains, upgrades)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: roadmap-api-pdb, namespace: roadmap }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: roadmap-api } }
Common trap

A readiness probe failure removes the Pod from the Service's endpoints (traffic stops routing to it) without killing it. A liveness probe failure kills and restarts the Pod. Confusing the two either kills healthy-but-slow-starting Pods or keeps sending traffic to a broken one.
