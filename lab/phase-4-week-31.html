1Stand up an EKS cluster (eksctl or Terraform)

Fastest path: eksctl
eksctl create cluster \
  --name roadmap-eks --region us-east-1 \
  --nodegroup-name standard-workers \
  --node-type t3.medium --nodes 2 --nodes-min 2 --nodes-max 4

aws eks update-kubeconfig --name roadmap-eks --region us-east-1
kubectl get nodes
The equivalent, reproducibly, in Terraform (fits the Phase 3 habit)
resource "aws_eks_cluster" "roadmap" {
  name     = "roadmap-eks"
  role_arn = aws_iam_role.eks_cluster.arn
  vpc_config { subnet_ids = module.vpc.private_subnet_ids }
}

resource "aws_eks_node_group" "standard" {
  cluster_name    = aws_eks_cluster.roadmap.name
  node_group_name = "standard-workers"
  subnet_ids      = module.vpc.private_subnet_ids
  scaling_config { desired_size = 2, min_size = 2, max_size = 4 }
}
Checkpoint

Deploy the Week 30 manifests (Deployment, Service, Ingress, ConfigMap, Secret, PVC) unmodified to this real EKS cluster and confirm they work exactly like they did on kind — that consistency is the entire value proposition of Kubernetes.

2IAM Roles for Service Accounts (IRSA); node groups vs Fargate

IRSA — let a Pod assume an IAM role without static credentials
eksctl create iamserviceaccount \
  --cluster roadmap-eks --namespace roadmap \
  --name roadmap-api-sa \
  --attach-policy-arn arn:aws:iam::<ACCOUNT_ID>:policy/CapstoneBucketRW \
  --approve
Reference it from the Deployment's Pod spec
      serviceAccountName: roadmap-api-sa
Node groups vs Fargate — pick per-workload, not cluster-wide
Node groups (EC2)   You manage capacity and patching, cheaper at steady/high utilization
Fargate             No node management, per-pod billing, simpler ops, costs more at scale

IRSA solves the same problem the Week 7-8 IAM role work solved for EC2, just for Pods: the application gets short-lived, automatically rotated credentials scoped to exactly what it needs, instead of a long-lived access key baked into a Secret.
