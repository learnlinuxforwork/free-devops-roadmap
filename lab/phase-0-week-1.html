1Install RHEL 10 or Rocky Linux 10 on a real machine

Use a real machine or a VM on Proxmox/VirtualBox — see the Home Lab section on the main roadmap for hardware options. Rocky Linux is a free, bug-for-bug compatible rebuild of RHEL, so everything here applies to either distro.

Download the ISO and write it to a USB drive with dd (Linux/macOS) or balenaEtcher (any OS). Do not use disk-imaging tools that aren't purpose-built for bootable USB creation.

Write the ISO to USB (macOS/Linux — replace /dev/diskX with your actual device)
# Find the device — DOUBLE CHECK this before running dd, it is destructive
diskutil list                       # macOS
lsblk                                # Linux

# Unmount it first (macOS)
diskutil unmountDisk /dev/diskX

# Write the ISO — bs=4m keeps this reasonably fast without being reckless
sudo dd if=Rocky-10-x86_64-dvd.iso of=/dev/rdiskX bs=4m status=progress
sync
After first boot, verify the install
cat /etc/os-release
uname -r
sudo dnf update -y
sudo dnf install -y vim git curl wget bash-completion
Checkpoint

You can SSH into the machine from your main computer, and sudo dnf update -y completes without error. If networking isn't up yet, that's Week 3 — for now, static config from the installer or DHCP is fine.

2Filesystem hierarchy, navigation, redirection, pipes, grep/sed/awk

Everything in Linux hangs off a single root /. Know what lives where before you touch anything else:

/bin, /usr/bin      user commands (symlinked together on modern RHEL)
/sbin, /usr/sbin    system administration commands
/etc                system-wide configuration files
/var                variable data: logs (/var/log), spool, cache
/home               user home directories
/root               root's home directory
/tmp                world-writable temp storage, cleared on reboot
/opt                third-party / optional software
/proc, /sys         virtual filesystems exposing kernel and process state
Navigation
pwd                       # print working directory
ls -la                    # long listing, include dotfiles
cd /var/log               # absolute path
cd -                      # jump back to the previous directory
cd ..                     # up one level
find /etc -name "*.conf"  # find files by name
find / -mtime -1 2>/dev/null   # files modified in the last day
Redirection and pipes
echo "hello" > file.txt        # overwrite
echo "again" >> file.txt       # append
command 2> errors.log          # redirect stderr only
command > out.log 2>&1         # redirect both stdout and stderr to the same file
command < input.txt            # feed a file in as stdin

ps aux | grep sshd             # pipe: filter process list
dmesg | tail -20               # last 20 kernel log lines
cat /var/log/messages | wc -l  # count lines
grep — search text
grep "error" /var/log/messages
grep -i "error" /var/log/messages       # case-insensitive
grep -r "TODO" /etc/                    # recursive
grep -v "^#" /etc/ssh/sshd_config       # invert match — exclude comments
grep -c "Failed password" /var/log/secure   # count matches
grep -E "fail(ed|ure)" /var/log/secure  # extended regex
sed — stream editor
sed 's/foo/bar/' file.txt          # replace first match per line
sed 's/foo/bar/g' file.txt         # replace all matches per line
sed -i.bak 's/foo/bar/g' file.txt  # edit in place, keep a .bak backup
sed -n '5,10p' file.txt            # print only lines 5-10
sed '/^#/d' file.txt               # delete comment lines
awk — field processing
awk '{print $1}' /etc/passwd -F:          # not valid — -F comes before the file
awk -F: '{print $1}' /etc/passwd          # print field 1, colon-delimited
awk -F: '{print $1, $3}' /etc/passwd      # username and UID
awk -F: '$3 >= 1000 {print $1}' /etc/passwd   # human user accounts only
df -h | awk '{print $5, $6}'              # disk usage % and mount point
Checkpoint

Write a one-liner that lists every user with UID >= 1000 from /etc/passwd, sorted alphabetically, using awk piped into sort. If you can do that without looking it up, this task is done.

3File permissions, ownership, umask, ACLs; hard vs symbolic links

Reading permissions
ls -l file.txt
# -rw-r--r-- 1 shea devops 220 Jul 25 10:00 file.txt
#  |  |  |
#  |  |  +-- other: read
#  |  +----- group: read
#  +-------- owner: read, write
# type(-) | owner(rwx) | group(rwx) | other(rwx)
chmod — symbolic and octal
chmod u+x script.sh          # add execute for owner
chmod g-w file.txt            # remove write from group
chmod o=r file.txt             # set other to read-only
chmod 755 script.sh            # rwxr-xr-x — owner all, group/other read+execute
chmod 644 file.txt             # rw-r--r-- — standard file default
chmod -R 750 /srv/app          # recursive
Ownership
chown shea file.txt
chown shea:devops file.txt
chgrp devops file.txt
chown -R shea:devops /srv/app
umask — default permission mask
umask                # show current mask, e.g. 0022
umask 0027            # new files: 640, new dirs: 750
# Files start at 666, dirs at 777; umask subtracts bits.
# Set permanently in ~/.bashrc or /etc/profile
ACLs — permissions beyond owner/group/other
setfacl -m u:jordan:rx /srv/app        # give user jordan read+execute
setfacl -m g:auditors:r /srv/app       # give group auditors read
getfacl /srv/app                        # view all ACL entries
setfacl -x u:jordan /srv/app            # remove jordan's entry
setfacl -b /srv/app                     # strip all ACLs
Hard vs symbolic links
ln original.txt hardlink.txt      # hard link: same inode, same data
ln -s original.txt symlink.txt    # symbolic link: a pointer to a path

ls -li original.txt hardlink.txt  # note the identical inode number
rm original.txt                   # hardlink.txt still has the data
                                   # symlink.txt is now broken (dangling)
Common trap

Hard links can't cross filesystems and can't point to directories. Symlinks can do both, but break if the target moves or is deleted. Know which one a task calls for — this is a frequent RHCSA gotcha.

4Lab: recover a system you locked yourself out of

Do this deliberately, on a VM or spare machine you can afford to break. Set a root password, then forget it on purpose, then recover it. This is a standard RHCSA objective and a real skill — you will do this for real, eventually, at 2am.

Step 1 — interrupt GRUB and edit the boot entry
# Reboot, and at the GRUB menu press 'e' to edit the highlighted entry
# Find the line starting with "linux" and append at the end:
rd.break

# Then press Ctrl+X (or F10) to boot with that change
Step 2 — remount root read-write and chroot in
mount -o remount,rw /sysroot
chroot /sysroot
Step 3 — reset the password and set the SELinux relabel flag
passwd root
# enter a new password twice

touch /.autorelabel
exit
exit
# system reboots
Why /.autorelabel matters

Inside the rd.break shell, SELinux isn't fully initialized, so any file you edit — including /etc/shadow via passwd — gets the wrong SELinux context. /.autorelabel forces a full relabel of the filesystem on next boot, which fixes the context. Skip this and you'll likely get locked out of login again by SELinux denials.

Checkpoint

You can log in with the new root password after reboot, and sudo ausearch -m avc -ts recent shows no denials related to /etc/shadow. Do this lab twice from memory before moving on — Week 4's RHCSA mock exam will not give you these steps.
