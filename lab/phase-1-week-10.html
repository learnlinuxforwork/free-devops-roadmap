1RDS (Postgres/MySQL) setup, multi-AZ concept, snapshots

Create a Multi-AZ Postgres instance
aws rds create-db-instance \
  --db-instance-identifier roadmap-db \
  --db-instance-class db.t3.micro \
  --engine postgres \
  --master-username roadmapadmin --master-user-password '<STRONG_PASSWORD>' \
  --allocated-storage 20 \
  --multi-az \
  --vpc-security-group-ids sg-xxxx
Snapshots — your rollback plan
aws rds create-db-snapshot \
  --db-instance-identifier roadmap-db --db-snapshot-identifier roadmap-db-pre-migration

aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier roadmap-db-restored \
  --db-snapshot-identifier roadmap-db-pre-migration

Multi-AZ isn't a read-replica or a performance feature — it's a synchronously replicated standby in a second AZ that RDS fails over to automatically if the primary has a problem. You pay roughly double for it; that's the cost of the SLA.

Checkpoint

Trigger a manual failover with aws rds reboot-db-instance --db-instance-identifier roadmap-db --force-failover and time how long the connection is actually interrupted.

2DynamoDB basics: partition keys, GSIs, on-demand vs provisioned

Create a table with a partition key and a sort key
aws dynamodb create-table \
  --table-name Orders \
  --attribute-definitions \
    AttributeName=CustomerId,AttributeType=S \
    AttributeName=OrderDate,AttributeType=S \
  --key-schema \
    AttributeName=CustomerId,KeyType=HASH \
    AttributeName=OrderDate,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST
Add a Global Secondary Index to query by a different attribute
aws dynamodb update-table --table-name Orders \
  --attribute-definitions AttributeName=Status,AttributeType=S \
  --global-secondary-index-updates '[{
    "Create": {
      "IndexName": "StatusIndex",
      "KeySchema": [{"AttributeName":"Status","KeyType":"HASH"}],
      "Projection": {"ProjectionType":"ALL"}
    }}]'
Write and read an item
aws dynamodb put-item --table-name Orders --item '{
  "CustomerId": {"S": "cust-42"},
  "OrderDate": {"S": "2026-07-25"},
  "Status": {"S": "shipped"}
}'

aws dynamodb query --table-name Orders \
  --key-condition-expression "CustomerId = :c" \
  --expression-attribute-values '{":c":{"S":"cust-42"}}'
Common trap

The partition key determines how DynamoDB distributes your data across physical partitions. A low-cardinality partition key (like Status with only 3-4 possible values) creates hot partitions — pick keys with high, evenly distributed cardinality.

3SQS and SNS: decouple two of your Week 6 scripts using a queue

Create a queue and a topic
aws sqs create-queue --queue-name roadmap-events
aws sns create-topic --name roadmap-alerts
Wire the Week 6 API poller to publish onto the queue instead of just logging
import boto3

sqs = boto3.client("sqs")
QUEUE_URL = "https://sqs.us-east-1.amazonaws.com/<ACCOUNT_ID>/roadmap-events"

def publish_event(status_code, latency_ms):
    sqs.send_message(
        QueueUrl=QUEUE_URL,
        MessageBody=f'{{"status": {status_code}, "latency_ms": {latency_ms}}}',
    )
A second script that consumes from the queue — the decoupled downstream
import boto3

sqs = boto3.client("sqs")
QUEUE_URL = "https://sqs.us-east-1.amazonaws.com/<ACCOUNT_ID>/roadmap-events"

while True:
    resp = sqs.receive_message(QueueUrl=QUEUE_URL, MaxNumberOfMessages=5, WaitTimeSeconds=10)
    for msg in resp.get("Messages", []):
        print("Processing:", msg["Body"])
        sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=msg["ReceiptHandle"])
Checkpoint

Kill the consumer script, let the poller keep publishing for a minute, then restart the consumer and watch it drain the backlog. That's the entire point of a queue — the producer never has to know or care whether the consumer is alive.
