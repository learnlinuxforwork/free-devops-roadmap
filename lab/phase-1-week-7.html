1Global infrastructure (regions/AZs), shared responsibility model

Every AWS service lives in one or more Regions, each made of multiple isolated Availability Zones (AZs) connected by low-latency links. Pick a home region and stick with it for this roadmap so resources aren't scattered.

Explore what's actually available near you
aws configure                              # set default region, output format, credentials
aws sts get-caller-identity                # confirm which account/identity you're using
aws ec2 describe-regions --output table
aws ec2 describe-availability-zones --region us-east-1 --output table

Shared responsibility model: AWS secures the infrastructure “of” the cloud — physical data centers, hardware, the hypervisor, managed-service internals. You're responsible “in” the cloud — IAM policies, security group rules, OS patching on EC2, data encryption choices, and anything in application code. A misconfigured S3 bucket is never AWS's failure to secure — it's a shared-responsibility miss on the customer side.

Checkpoint

Explain, without notes, one thing AWS is responsible for and one thing you're responsible for on EC2, and the same pair for a managed service like RDS. The split is different for each.

2IAM: users, groups, roles, policies; enable MFA on root

Groups and users — never attach policies to a user directly
aws iam create-group --group-name Developers
aws iam attach-group-policy --group-name Developers \
  --policy-arn arn:aws:iam::aws:policy/PowerUserAccess

aws iam create-user --user-name jordan
aws iam add-user-to-group --user-name jordan --group-name Developers
aws iam create-login-profile --user-name jordan --password-reset-required
A least-privilege custom policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::capstone-app-bucket/*"
  }]
}
Create the policy and a role that can assume it
aws iam create-policy --policy-name CapstoneBucketRW \
  --policy-document file://capstone-bucket-policy.json

aws iam create-role --role-name CapstoneAppRole \
  --assume-role-policy-document file://trust-policy.json
aws iam attach-role-policy --role-name CapstoneAppRole \
  --policy-arn arn:aws:iam::<ACCOUNT_ID>:policy/CapstoneBucketRW
Enable MFA on the root user (console, not CLI, by design)
1. Sign in as the root user (only use root for this one task)
2. IAM console -> top-right account name -> Security credentials
3. Assign MFA device -> Authenticator app (or a hardware key if you have one)
4. Scan the QR code, enter two consecutive codes to confirm
5. Never use root day-to-day again after this -- use an IAM user with admin policy instead
Common trap

AWS deliberately makes root-account MFA a console-only flow — there's no CLI shortcut, and that's intentional friction around your most powerful credential.

3Set up AWS Organizations plus a sandbox account with a budget alarm

Create an organization and a member account
aws organizations create-organization --feature-set ALL
aws organizations create-account \
  --email sandbox+aws@yourdomain.com \
  --account-name "Roadmap Sandbox"
aws organizations list-accounts --output table
A budget that emails you before you get surprised
{
  "BudgetName": "sandbox-monthly-cap",
  "BudgetLimit": {"Amount": "20", "Unit": "USD"},
  "TimeUnit": "MONTHLY",
  "BudgetType": "COST"
}
Create it and attach a notification
aws budgets create-budget \
  --account-id <ACCOUNT_ID> \
  --budget file://budget.json \
  --notifications-with-subscribers file://notifications.json
Checkpoint

A budget alarm exists and you've confirmed it by (temporarily) lowering the threshold below current spend to see the email actually arrive, then setting it back to a sane value.
