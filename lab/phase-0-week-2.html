1Users, groups, sudo policy, password aging, /etc/skel

Three files back every user and group on the system. Know their format cold:

# /etc/passwd — username:x:UID:GID:comment:home:shell
shea:x:1000:1000:Shea Bennett:/home/shea:/bin/bash

# /etc/shadow — username:hashed_password:lastchange:min:max:warn:inactive:expire
shea:$6$abc...:19900:0:99999:7:::

# /etc/group — groupname:x:GID:members
devops:x:1001:shea,jordan
Creating and managing users
useradd -m -c "Shea Bennett" -s /bin/bash shea    # -m creates home dir from /etc/skel
passwd shea                                        # set initial password
usermod -aG devops shea                            # add to a supplementary group (-a = append, don't overwrite)
usermod -L shea                                     # lock the account
usermod -U shea                                     # unlock it
userdel -r shea                                     # delete user and their home dir
id shea                                              # show UID, GID, and group memberships
groups shea                                          # show group memberships only
Groups
groupadd devops
groupadd -g 2000 auditors     # explicit GID
groupdel auditors
gpasswd -a shea devops        # alternate way to add a user to a group
sudo policy
visudo                          # always edit sudoers this way — it validates syntax before saving
# Grant full sudo via the wheel group (RHEL/Rocky default):
usermod -aG wheel shea

# Or scope a specific command in /etc/sudoers.d/ (preferred over editing sudoers directly):
echo 'jordan ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx' > /etc/sudoers.d/jordan-nginx
visudo -cf /etc/sudoers.d/jordan-nginx    # validate a specific file
Password aging
chage -l shea                    # list current aging settings
chage -M 90 shea                 # max password age: 90 days
chage -m 1 shea                  # min days between changes
chage -W 7 shea                  # warn 7 days before expiry
chage -E 2026-12-31 shea         # set an account expiration date
chage -d 0 shea                  # force password change at next login
/etc/skel
# Anything placed in /etc/skel is copied into new users' home directories
# by useradd -m. Use it to seed default dotfiles or a standard directory layout.
cp /etc/bashrc.company /etc/skel/.bashrc
mkdir -p /etc/skel/{Projects,Scripts}
useradd -m newhire     # newhire's home now has .bashrc, Projects/, Scripts/
Checkpoint

Create a user who can run systemctl restart httpd via sudo with no password prompt, but has no other sudo rights. Verify with sudo -l -U that user's name.

2systemd: units, targets, systemctl, journald log analysis

Managing services
systemctl status sshd
systemctl start sshd
systemctl stop sshd
systemctl restart sshd
systemctl reload sshd            # re-read config without dropping connections
systemctl enable sshd            # start on boot
systemctl disable sshd
systemctl enable --now sshd      # enable and start in one command
systemctl is-active sshd
systemctl is-enabled sshd
A minimal custom unit file
# /etc/systemd/system/api-poller.service
[Unit]
Description=Poll the internal API every run
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
User=shea
ExecStart=/usr/local/bin/api-poller.sh
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
systemctl daemon-reload           # required after creating/editing a unit file
systemctl enable --now api-poller.service
Targets (systemd's equivalent of runlevels)
systemctl get-default                    # show the default target
systemctl set-default multi-user.target  # boot to CLI, no GUI
systemctl isolate multi-user.target      # switch right now, without rebooting
systemctl list-units --type=target       # see all active targets
journald log analysis
journalctl -u sshd                  # logs for one unit
journalctl -u sshd -f               # follow, like tail -f
journalctl --since "1 hour ago"
journalctl --since today --until "10 minutes ago"
journalctl -p err                   # priority: err and above
journalctl -b                       # logs since last boot
journalctl -b -1                    # logs from the previous boot
journalctl --disk-usage
journalctl --vacuum-time=7d         # trim logs older than 7 days
Checkpoint

Write a unit file for a script of your own, enable it, confirm it starts on boot with systemctl is-enabled, then find its exact failure reason in journalctl -u after intentionally breaking the script path.

3Package management with dnf/yum, repos, and module streams

Core dnf commands
dnf search nginx
dnf info nginx
dnf install -y nginx
dnf remove -y nginx
dnf update -y                     # update everything
dnf update -y nginx               # update one package
dnf list installed | grep nginx
dnf history                       # every transaction, numbered
dnf history undo 42                # roll back transaction 42
dnf provides */ip                  # which package provides the `ip` command
Repo configuration
# /etc/yum.repos.d/internal.repo
[internal-tools]
name=Internal Tools Repo
baseurl=https://repo.internal.example.com/rhel10/x86_64/
enabled=1
gpgcheck=1
gpgkey=https://repo.internal.example.com/RPM-GPG-KEY
dnf repolist                       # list enabled repos
dnf repolist all                   # including disabled
dnf config-manager --set-enabled internal-tools
dnf clean all                      # clear cached metadata
Module streams
dnf module list postgresql          # see available versions/streams
dnf module info postgresql:16
dnf module enable postgresql:16
dnf module install postgresql:16/server
dnf module reset postgresql         # back out and pick a different stream
Common trap

Only one stream per module can be enabled at a time. If you need Node 18 for one project and Node 20 for another on the same host, module streams won't solve that — reach for containers instead. That tension is exactly why Phase 4 exists.

4Scheduled tasks: cron, anacron, systemd timers

crontab syntax
# minute hour day-of-month month day-of-week   command
# *      *    *            *     *
0 2 * * *        /usr/local/bin/backup.sh          # every day at 2:00 AM
*/15 * * * *     /usr/local/bin/health-check.sh     # every 15 minutes
0 9 * * 1-5      /usr/local/bin/weekday-report.sh   # 9 AM, Mon-Fri
0 0 1 * *        /usr/local/bin/monthly-cleanup.sh  # midnight on the 1st
crontab -e            # edit your own crontab
crontab -l            # list your crontab
crontab -u shea -l     # list another user's (as root)
crontab -r             # remove your crontab entirely — no confirmation prompt
System-wide cron and anacron
/etc/crontab               # system crontab, includes a user field
/etc/cron.d/                # drop-in files, same format as /etc/crontab
/etc/cron.daily/            # scripts run once a day via anacron
/etc/cron.hourly/
/etc/cron.weekly/
/etc/cron.monthly/
/etc/anacrontab              # anacron's own schedule — catches up missed jobs
                              # after a machine that was off comes back on
systemd timers — the modern alternative to cron
# /etc/systemd/system/backup.timer
[Unit]
Description=Run backup.service daily at 2am

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
systemctl enable --now backup.timer
systemctl list-timers                 # see all active timers and next run time
journalctl -u backup.service          # the timer's paired .service still logs normally
Checkpoint

Systemd timers log to journald automatically and support Persistent=true, which catches up a missed run after downtime — cron can't do that natively. Know when to reach for each: cron for simple, portable one-liners; timers when you need dependency ordering, resource limits, or better observability.
