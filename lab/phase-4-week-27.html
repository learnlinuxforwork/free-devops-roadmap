1Images vs containers, Dockerfile best practices, multi-stage builds

An image is a read-only, layered filesystem snapshot. A container is a running (or stopped) process using that image plus a thin writable layer on top. One image, many containers — same relationship as a class and its instances.

A multi-stage Dockerfile — build tools never ship in the final image
# ---- build stage ----
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

# ---- final stage ----
FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
Build it and compare layer sizes
docker build -t roadmap-api:v1 .
docker images roadmap-api
docker history roadmap-api:v1
Common trap

Copying . . before installing dependencies busts the layer cache on every single code change, forcing a full dependency reinstall each build. Copy dependency manifests first, install, THEN copy the rest of the source.

2Container networking and volumes; how namespaces and cgroups actually work

Networking modes
docker network create roadmap-net
docker run -d --name api --network roadmap-net roadmap-api:v1
docker run -d --name db --network roadmap-net postgres:16
# containers on the same user-defined network resolve each other by container name -- "db" just works
Volumes — data that outlives the container
docker volume create roadmap-db-data
docker run -d --name db -v roadmap-db-data:/var/lib/postgresql/data postgres:16
docker volume inspect roadmap-db-data

Under the hood, a container is just a regular Linux process with two kernel features applied: namespaces give it an isolated view of PIDs, network interfaces, mounts, and hostname (it thinks it's alone on the machine), and cgroups cap how much CPU, memory, and I/O it's allowed to use. There's no container-specific kernel — it's the same Linux you drilled in Phase 0, just fenced off.

Checkpoint

Run ps aux on the Docker host and find your container's process — it's a normal PID in the host's process table, just invisible from inside the container's own PID namespace.
