1Learn Scrum ceremonies and Kanban; set up a Jira or GitHub Projects board

The Scrum ceremonies, in one line each
Sprint Planning    Decide what gets built this sprint, from the backlog
Daily Standup      3 questions: done yesterday, doing today, blockers
Sprint Review       Demo what shipped to stakeholders
Retrospective       What went well, what didn't, one concrete change for next sprint
Set up a GitHub Projects board for the capstone
gh project create --owner <you> --title "Capstone Roadmap"
gh project field-create <PROJECT_NUM> --owner <you> \
  --name Status --data-type SINGLE_SELECT \
  --single-select-options "Backlog,In Progress,In Review,Done"

Kanban skips the fixed-length sprint and just limits work-in-progress per column — pick Kanban for solo capstone work where a rigid 2-week sprint boundary adds ceremony without adding value; pick Scrum when coordinating a team needs the shared rhythm.

2Write ADRs (architecture decision records) for 2–3 capstone decisions

An ADR template — short, dated, and honest about tradeoffs
# ADR 003: Choose Terraform over CloudFormation for capstone infrastructure

Date: 2026-07-25
Status: Accepted

## Context
Need to provision VPC, EKS, and RDS reproducibly across dev/staging/prod.

## Decision
Use Terraform with S3 + DynamoDB remote state.

## Consequences
+ Multi-cloud portability if ever needed; large module ecosystem
- Extra state-backend setup CloudFormation wouldn't require
- Team must learn HCL in addition to AWS itself
Checkpoint

Write ADRs for your Terraform-vs-CloudFormation call (Week 24), your DR strategy choice (Week 16), and one more decision of your choosing. Commit them to docs/adr/ — this is one of the highest-signal things a hiring manager can read in your repo.

3Practice a mock design review or code review with a peer or mentor

Find someone — a study partner from The Hood, a mentor, even a knowledgeable friend — and walk them through your capstone architecture live, or have them review a real PR. The goal is practicing explaining tradeoffs out loud under mild real-time pressure, which is a different skill than writing the ADR alone.

A short structure that keeps a design review focused
1. Context: what problem does this solve, in one sentence
2. Approach: what you built and why, referencing the relevant ADR
3. Alternatives considered: what you didn't pick, and why
4. Open questions: what you're still unsure about
5. Q&A
Checkpoint

This is explicitly interview practice — the design-review format above is close to what a real system-design interview looks like. Do it at least once before Phase 8's capstone finalization.
