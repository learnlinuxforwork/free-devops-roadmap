1Ship container logs via Fluent Bit to OpenSearch or CloudWatch Logs

Fluent Bit as a DaemonSet, shipping to CloudWatch Logs
helm repo add fluent https://fluent.github.io/helm-charts
helm install fluent-bit fluent/fluent-bit -n logging --create-namespace \
  --set config.outputs='[OUTPUT]\n    Name cloudwatch_logs\n    Match *\n    region us-east-1\n    log_group_name /roadmap/eks\n    log_stream_prefix pod-'
Or point it at OpenSearch instead
[OUTPUT]
    Name  opensearch
    Match *
    Host  search-roadmap-xxxx.us-east-1.es.amazonaws.com
    Port  443
    Index roadmap-logs
    tls   On

A DaemonSet means one Fluent Bit Pod per node, tailing every container's stdout/stderr locally and forwarding it — the same pattern as journalctl centralization you'd set up for a fleet of plain EC2 instances, just running inside the cluster.

2Practice log-based troubleshooting on an intentionally broken deploy

Break something on purpose, then find it purely from logs
# e.g. deploy a version with a wrong DATABASE_URL
helm upgrade roadmap-api ./charts/roadmap-api --set env.DATABASE_URL=postgres://wrong -n roadmap
Find it via CloudWatch Logs Insights instead of kubectl logs
fields @timestamp, @message
| filter @message like /connection refused/ or @message like /ERROR/
| sort @timestamp desc
| limit 50
Checkpoint

Diagnose the root cause from logs alone, without running kubectl describe or kubectl exec — that's the actual skill this task is building. When the on-call phone rings, you often don't have cluster access yet; logs arrive first.
