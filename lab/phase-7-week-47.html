1Enable GuardDuty, Security Hub, and AWS Config with conformance packs

Turn on threat detection and centralized findings
aws guardduty create-detector --enable
aws securityhub enable-security-hub --enable-default-standards
AWS Config, with a conformance pack enforcing a real standard
aws configservice put-configuration-recorder \
  --configuration-recorder name=default,roleARN=arn:aws:iam::<ACCOUNT_ID>:role/config-role \
  --recording-group allSupported=true
aws configservice start-configuration-recorder --configuration-recorder-name default

aws configservice put-conformance-pack \
  --conformance-pack-name operational-best-practices \
  --template-s3-uri s3://aws-configservice-us-east-1/cp-templates/Operational-Best-Practices-for-CIS-AWS-v1.4-Level1.yaml
Checkpoint

Intentionally create one non-compliant resource (a public S3 bucket, an unencrypted EBS volume) and watch it surface as a finding in Security Hub within a few minutes — then fix it and confirm the finding clears.

2Set up Ansible for configuration management and patching on a small EC2 fleet

An inventory and a playbook — this is where Phase 0 pays off directly
# inventory.ini
[webservers]
10.0.1.10 ansible_user=ec2-user
10.0.1.11 ansible_user=ec2-user
playbook.yml — patch and harden, idempotently
- hosts: webservers
  become: true
  tasks:
    - name: Update all packages
      dnf: { name: '*', state: latest }
    - name: Ensure firewalld is running
      systemd: { name: firewalld, state: started, enabled: true }
    - name: Deploy the app config
      template:
        src: app.conf.j2
        dest: /etc/roadmap/app.conf
      notify: restart app
  handlers:
    - name: restart app
      systemd: { name: roadmap-app, state: restarted }
Run it
ansible-playbook -i inventory.ini playbook.yml --check   # dry run first
ansible-playbook -i inventory.ini playbook.yml

Every command in this playbook is something you ran by hand with SSH back in Phase 0 — dnf update, systemctl, editing config files. Ansible's entire value is running that same knowledge idempotently, at fleet scale, from a diffable YAML file instead of tribal knowledge in someone's head.

3Review least-privilege IAM patterns across the whole capstone project

Find over-privileged roles with IAM Access Analyzer
aws accessanalyzer create-analyzer --analyzer-name capstone-analyzer --type ACCOUNT
aws accessanalyzer list-findings --analyzer-arn <ANALYZER_ARN>
Generate a right-sized policy from actual CloudTrail usage instead of guessing
aws accessanalyzer start-policy-generation \
  --policy-generation-details principalArn=arn:aws:iam::<ACCOUNT_ID>:role/CapstoneAppRole \
  --cloud-trail-details '{"trails":[{"cloudTrailArn":"<TRAIL_ARN>","region":"us-east-1"}],
    "startTime":"2026-06-01T00:00:00Z","endTime":"2026-07-25T00:00:00Z"}'
Checkpoint

Pick the single most over-privileged role in your capstone (it's probably one you attached PowerUserAccess to back in Week 7 to move fast) and replace it with a generated least-privilege policy.

4Harden a Linux host: SSH policy, firewalld, SELinux enforcing, CIS baseline

SSH hardening — /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
AllowUsers roadmapadmin
MaxAuthTries 3
ClientAliveInterval 300
ClientAliveCountMax 2
Confirm firewalld and SELinux are both actually enforcing
sudo systemctl restart sshd
firewall-cmd --state
firewall-cmd --list-all
getenforce                     # must say Enforcing, not Permissive or Disabled
A CIS-benchmark-style scan to find what you missed
sudo dnf install -y openscap-scanner scap-security-guide
sudo oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_cis \
  --results scan-results.xml /usr/share/xml/scap/ssg/content/ssg-rl10-ds.xml
Checkpoint

Everything in this task is Phase 0 material applied under an explicit compliance frame — SSH config, firewalld, SELinux. That's the whole arc of this roadmap in one task: the Linux fundamentals were never optional background, they're the foundation everything after Phase 0 stands on.
